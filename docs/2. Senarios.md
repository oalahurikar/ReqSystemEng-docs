# Best Practices: Scenario Design & Management

## 1. The Role of Scenarios in RDD
In this project, a **Scenario** is not just a user story. It is the **"World State"** container.

While a **JTBD** defines the *Goal* (Why), the **Scenario** defines the *Conditions* (Where/When).
*   **The Problem:** Requirements like "System shall be fast" are meaningless without context.
*   **The Solution:** Scenarios act as the "Physics Engine" for your requirements. A requirement is only valid *inside* a specific Scenario.

> **Formula:** `Scenario = Narrative (ConOps) + Variables (Constraints)`

---

## 2. Anatomy of a Scenario
Every Scenario must possess the following four components to be valid in the Graph.

### A. The ID (The Anchor)
Engineers and AI need a shorthand handle. Do not use UUIDs.
*   **Format:** `SCN-{CATEGORY}-{ID}`
*   **Examples:**
    *   `SCN-NOM-01` (Nominal operation)
    *   `SCN-ERR-05` (Error state / Failure mode)
    *   `SCN-ENV-09` (Environmental stressor)

### B. The Variables (The Physics)
Define the specific state of the world. These are the "Knobs" you turn to stress the system.
*   **Example for Software:** `{ "User_Level": "Junior", "Data_Scale": "50k_Items", "Git_Connection": "Offline" }`
*   **Example for Hardware:** `{ "Wind": "15m/s", "GPS": "Denied", "Battery": "15%" }`

### C. The Narrative (The ConOps)
A brief "Day in the Life" description. It provides the human context for *why* these variables matter.
*   *Example:* "The user attempts to link a requirement during a merge conflict while the Git server is offline."

### D. The Traceability (The Spine)
Scenarios must connect to the rest of the graph:
1.  **Upstream (Validates JTBD):** One Job (Value) is tested against multiple Scenarios (Contexts).
2.  **Downstream (Context for L2):** L2 Requirements link *to* Scenarios.
    *   *Rule:* "Latency < 200ms" (Linked to `SCN-NOM-01`)
    *   *Rule:* "Latency < 1000ms" (Linked to `SCN-ERR-05`)

---

## 3. Best Practices for Writing Scenarios

### Step 1: Define Your "Operational Variables" First
Before writing narratives, list the variables that break your system.
*   **Nominal:** The Happy Path.
*   **Stress:** Maximum Load, Dirty Data, Hardware Failure, Edge Cases.

### Step 2: Create the "Scenario Matrix"
Don't write random stories. Systematically map your JTBDs to your Stress Variables.
*   **Scenario A (Basic):** JTBD-1 + Nominal Variables.
*   **Scenario B (Stress):** JTBD-1 + High Load + Low Network.
*   **Scenario C (Corner):** JTBD-2 + Invalid Input + Expert User.

### Step 3: Write "Validation Gates," Not Just Stories
Write the scenario such that it clearly defines **Success** and **Failure**.
*   *Bad:* "The user tries to load the file."
*   *Good:* "The user loads a 5GB file. The system must either load it within 5s or display a 'File Too Large' error. It must not crash."

---

## 4. How to Fit Scenarios into the Project Structure

### File Location
Store scenarios in: `requirements/Scenarios/`.
*   One file per major Scenario Group, or one index file for simple projects.

### The Traceability Workflow
1.  **Define JTBD:** "User needs to trace requirements."
2.  **Define Scenarios:**
    *   `SCN-01`: Small project (10 items).
    *   `SCN-02`: Large project (10k items).
3.  **Draft L2 Requirements:**
    *   Req A: "Query time shall be < 1s" (Links to `SCN-01`).
    *   Req B: "Query time shall be < 5s" (Links to `SCN-02`).
4.  **Verification:**
    *   Test Case T-01 configures environment to match `SCN-01`.
    *   Test Case T-02 configures environment to match `SCN-02`.

### The "Physics" Check
When reviewing requirements, ask: **"Is this true in all Scenarios?"**
If the answer is "No," you must split the requirement and link it to the specific Scenario where it applies.
