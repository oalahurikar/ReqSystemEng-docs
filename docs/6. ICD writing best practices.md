# ICD Writing Best Practices: First Principles & Signal over Noise

## 1. First Principles: The Physics of the Interface
An Interface Control Document (ICD) is not "documentation." It is a **Contract** that polices the boundary between two autonomous nodes (e.g., Lidar Hardware vs. Perception Software).

* **The Principle of the Boundary:** 80% of system failures occur at the boundaries. If data crosses a wire, a protocol, or a team boundary, it must have a contract.
* **The Principle of the Handshake:** The ICD is the "handshake" that must be agreed upon *before* detailed component engineering (L3) begins.
* **The Principle of the "Pipe":** Do not document the *internal* state of a component. Only document what travels through the "pipe" connecting two components.

## 2. Signal over Noise: What to Include
Avoid bloating the ICD with implementation details. Focus strictly on the **observable properties** of the interface.

### ✅ Signal (Include this)
* **The Payload:** Precise data structure (e.g., `uint16`, `float64`).
* **The Physics:** Units (`RPM`, `m/s^2`), Range (`0-100`), and Resolution.
* **The Frequency:** How often the data moves (e.g., `100Hz`).
* **The Source & Target:** Explicit ownership (Who sends? Who reads?).

### ❌ Noise (Exclude this)
* **Internal Logic:** "The sensor reads the data by checking register X" (This belongs in L3 Component Specs).
* **Rationale/History:** "We chose 100Hz because..." (This belongs in Architecture Decision Records).
* **Vague Promises:** "System shall provide accurate data" (This is an untestable requirement, not a contract).

## 3. The "Consumer-Driven" Workflow
The most effective contracts are drafted by the **Consumer** (the entity that *needs* the data), not the Producer.

1. **Demand:** The Consumer (e.g., Navigation Node) defines the interface it needs: *"I need Velocity at 50Hz to close my control loop."*
2. **Negotiation:** The Producer (e.g., Motor Node) reviews the demand.
    * *Reject:* "I can only provide 30Hz."
    * *Accept:* "Agreed. Contract Signed."
3. **Lock:** Once agreed, the interface is **Frozen**. Any change requires a formal version increment and invalidates downstream components.

## 4. Timing: The "Sandwich" Rule
The ICD is the bridge between System Architecture (L2) and Component Design (L3).

* **Draft during L2:** As you define *what* the system does ("Motor shall report speed"), you must simultaneously define *how* that data looks (`uint16 RPM`).
* **Freeze before L3:** You cannot write valid L3 component requirements (e.g., "If speed > 5000...") until the input data type is contractually guaranteed.
* **Never Retrofit:** Writing the ICD *after* building the components guarantees integration hell.

## 5. Technical Execution: Single Source of Truth
The ICD must be the source of code, not a reflection of it.

* **Don't Manual Copy:** Never manually type structs into C++ headers based on a PDF.
* **Generate the Artifact:** The ICD tool/definition should **export** the `.h` file, `.json` schema, or `.proto` file.
* **Version Control:** If the ICD version changes (v1.0 → v1.1), the code fails to compile until the new contract is explicitly handled.
