# Edge Validation Matrix: Graph Schema Constraints
**First Principles & Best Practices**

---

## 1. First Principles: The Physics of Graph Constraints

An Edge Validation Matrix is not "documentation." It is a **Constraint Definition** that specifies which node types can be connected by which edge types, establishing the valid structure of the knowledge graph.

* **The Principle of Type Safety:** Not all edges are valid between all node types. A `VERIFIED_BY` edge from a `Requirement` to a `Component` is semantically invalid—it should connect `Requirement → TestCase`.
* **The Principle of Graph Integrity:** The graph structure must enforce domain logic. Invalid edges create "spaghetti graphs" that break traversal algorithms and semantic inference.
* **The Principle of Fail-Fast:** Invalid edge creation must be detected and blocked immediately at the graph boundary (The Governor), not deep inside query logic.

---

## 2. What is an Edge Validation Matrix?

### Definition

An Edge Validation Matrix is a table that defines:
- **Valid Edge Type → Node Type Pairings:** Which edge types can connect which source node types to which target node types
- **Invalid Pairings:** Explicitly blocked connections that violate domain semantics
- **Semantic Rules:** The logical meaning of each valid edge type pairing
- **Enforcement Point:** Where in the system these rules are validated (typically The Governor)

### Schema Validation vs. Edge Type Validation

**Schema Validation (What We Have):**
- Validates edge structure matches Pydantic model (`GraphEdge`)
- Checks field types: `source_uid` (UUID), `target_uid` (UUID), `type` (EdgeType enum)
- Example: "Is this edge correctly structured with valid UUIDs and enum value?"

**Edge Type Validation (What You Need):**
- Validates edge type is semantically valid for the source and target node types
- Checks node type compatibility before allowing edge creation
- Example: "Can a `DERIVED_FROM` edge connect a `Requirement` node to a `TestCase` node? Answer: No—`DERIVED_FROM` is only valid for `Requirement → Requirement`."

### The Gap

Your ICD-01 defines:
- ✅ **Node Types:** 7 types (Requirement, TestCase, Component, Parameter, Constraint, Job, Scenario)
- ✅ **Edge Types:** 6 types (Derived_From, Verified_By, Allocated_To, Constrains, Justifies, Defines_Context)
- ✅ **Edge Structure:** Source UID, Target UID, Edge Type, Context

But it doesn't define:
- ❌ **Edge Type Compatibility Matrix:** Which edge types can connect which node type pairs
- ❌ **Validation Logic:** How to check if an edge is valid before creation
- ❌ **Error Handling:** What error code/message when invalid edge is attempted

## 3. Why Use an Edge Validation Matrix?

### 1. Prevents Graph Corruption

**Without Edge Validation Matrix:**
- Developers or LLM agents can create semantically invalid edges (e.g., `DERIVED_FROM` from `Requirement` to `Constraint`)
- Graph queries fail silently or return incorrect results (traversing invalid edges)
- Constraint evaluation breaks (expecting `Requirement → Requirement` but finding `Requirement → Component`)
- Graph structure becomes "spaghetti"—connections have no semantic meaning

**With Edge Validation Matrix:**
- The Governor blocks invalid edge creation immediately
- Graph structure maintains semantic integrity
- Traversal algorithms work correctly (they assume valid edge types)
- Constraint evaluation works (edges connect expected node types)

**Example:**
```
❌ Without: LLM Orchestrator creates edge DERIVED_FROM from REQ-100 (Requirement) to CON-50 (Constraint)
           → Graph query "find all requirements Derived_From REQ-100" returns invalid result [CON-50]
           → Constraint evaluation breaks (expects Requirement, gets Constraint)

✅ With: Governor validates edge creation request
         → Checks: DERIVED_FROM requires source.type == Requirement AND target.type == Requirement
         → Detects: target.type == Constraint → INVALID
         → Blocks edge creation with error: "DERIVED_FROM edge can only connect Requirement → Requirement"
```

### 2. Enables Precise L3 Requirements

**Without Edge Validation Matrix:**
- L3 requirements are vague: "The Governor shall validate edges"
- Unclear validation logic: What exactly should be checked?
- Missing error handling: What error code when edge type is incompatible?

**With Edge Validation Matrix:**
- L3 requirements are precise: "The Governor shall validate edge type compatibility using Edge Validation Matrix (Section X). For `DERIVED_FROM` edges, source node must be `Requirement` and target node must be `Requirement`. If validation fails, return error code `INVALID_EDGE_TYPE_PAIRING`."
- Clear validation logic: Check node types match matrix before edge creation
- Defined error codes: `INVALID_EDGE_TYPE_PAIRING` with specific message indicating valid pairings

**Example L3 Requirement (with Edge Validation Matrix):**
```markdown
**L3-REQ-1.3.1: Edge Type Validation**

**Allocated Component:** The Governor (Constraint Rules module)
**Edge Validation Matrix Reference:** Section 4 (Valid Edge Type Pairings)

**WHAT:**
When an edge creation request is received, The Governor shall:
1. Retrieve source node type (query Graph Store for node.type by source_uid)
2. Retrieve target node type (query Graph Store for node.type by target_uid)
3. Validate edge type compatibility using Edge Validation Matrix:
   - Check if (source_node_type, edge_type, target_node_type) is valid pairing
   - If invalid, return error `INVALID_EDGE_TYPE_PAIRING` with message indicating valid target node types
4. If validation passes → proceed with edge creation
```

### 3. Prevents L3 Requirement Churn

**Without Edge Validation Matrix:**
- Edge validation rules are discovered during L3 implementation
- Rules change as implementation progresses (discover edge cases)
- L3 requirements need constant updates (churn)
- Graph queries and algorithms break when rules change

**With Edge Validation Matrix:**
- Edge validation rules are frozen before L3 implementation
- L3 requirements reference the matrix (stable specification)
- Changes to edge rules require matrix update first (controlled change)
- Graph structure remains stable (fewer breaking changes)

## 4. When to Create an Edge Validation Matrix

**Timing:** After ICD-01 (Graph Ontology) is defined, but **before** L3 component implementation begins.

**Process Stage:**
1. ✅ ICD-01 defined (Node Types, Edge Types, Graph Structure)
2. ✅ Workflow State Model defined (State Transitions)
3. ✅ Allocation Map created (Component Responsibilities)
4. 🎯 **EDGE VALIDATION MATRIX CREATED** ← You are here
5. ⏭️ L3 Requirements written (Component Specs with edge validation logic)

**Why This Order Matters:**
- You need ICD-01 to know what node types and edge types exist
- You need Workflow State Model to understand state constraints (e.g., Draft requirements cannot have certain edges)
- You need Allocation Map to know which component (The Governor) enforces edge validation
- You cannot write L3 edge validation requirements without knowing the valid pairings matrix
- Edge validation rules must be frozen before L3 implementation (prevents churn)

## 5. Without Edge Validation Matrix: What Happens?

### Problem 1: Graph Corruption

**Scenario:** LLM Orchestrator (Spider Mode) creates edge `VERIFIED_BY` from `Requirement` to `Component` (semantically invalid—should be `Requirement → TestCase`).

**Consequences:**
- Graph query "find all TestCases that verify REQ-100" returns incorrect results (includes Component nodes)
- Completeness check "find Requirements NOT Verified_By any Test" fails (misses Requirements with invalid Component edges)
- Graph structure becomes inconsistent—edges don't mean what algorithms expect

**Impact:** Broken graph queries, incorrect traceability, failed validation checks

### Problem 2: L3 Requirement Ambiguity

**Scenario:** L3 requirement says "The Governor shall validate edge types."

**Consequences:**
- Unclear what "validate" means—check structure? Check node types? Check semantics?
- Developers implement different validation logic (some check structure only, some check node types)
- Inconsistent behavior across system (some invalid edges pass, others fail)
- No clear error messages (generic "invalid edge" instead of "DERIVED_FROM requires Requirement → Requirement")

**Impact:** Inconsistent implementation, poor error messages, difficult debugging

### Problem 3: Implementation Churn

**Scenario:** Edge validation rules are discovered during L3 implementation.

**Consequences:**
- Rules change as edge cases are discovered (e.g., "Oh, we need to allow `CONSTRAINS` to connect `Constraint → Parameter` too")
- L3 requirements need constant updates (change validation logic)
- Graph queries break when rules change (assumed invalid edges become valid)
- Breaking changes cascade through system (code, tests, documentation)

**Impact:** Development churn, breaking changes, delayed delivery

### Problem 4: Broken Semantic Inference

**Scenario:** Invalid edges exist in graph (e.g., `DERIVED_FROM` from `Requirement` to `Constraint`).

**Consequences:**
- LLM Orchestrator (Spider Mode) infers relationships incorrectly (traverses invalid edges)
- Constraint evaluation fails (expects `Requirement → Requirement` but finds `Requirement → Constraint`)
- Impact analysis breaks (traverses invalid edges, includes wrong nodes in blast radius)
- Traceability queries return incorrect results (invalid node types in trace chain)

**Impact:** Broken AI inference, failed constraint validation, incorrect impact analysis

## 7. Edge Validation Matrix Structure

### Matrix Format

The Edge Validation Matrix is typically a table with three columns:

| Edge Type | Valid Source Node Type | Valid Target Node Type | Semantic Meaning |
|-----------|------------------------|------------------------|------------------|
| `DERIVED_FROM` | Requirement | Requirement | Parent-child hierarchy (L1 → L2 requirements) |
| `VERIFIED_BY` | Requirement | TestCase | Requirement is verified by test case |
| `ALLOCATED_TO` | Requirement | Component | Requirement is allocated to component for implementation |
| `CONSTRAINS` | Constraint | Requirement | Constraint governs requirement value |
| `JUSTIFIES` | Job | Requirement | Job (JTBD) justifies requirement (the "why") |
| `DEFINES_CONTEXT` | Scenario | Constraint | Scenario defines context when constraint applies |

### Additional Constraints

The matrix may also include:
- **State Constraints:** Certain edges may only be valid when nodes are in specific states (e.g., `DERIVED_FROM` edges only valid for Approved requirements)
- **Direction Constraints:** Edges are directed (source → target), so order matters
- **Cardinality Constraints:** Some edge types may have cardinality limits (e.g., Requirement can have only one parent via `DERIVED_FROM`)
- **Cycle Prevention:** Certain edge types may not allow cycles (e.g., `DERIVED_FROM` cannot create circular dependencies)

## 8. Implementation Notes

### Enforcement Point

**Component:** The Governor (Constraint Rules module)
- All edge creation requests pass through The Governor
- The Governor validates edge type compatibility using the matrix
- Invalid edges are blocked with specific error codes

### Validation Sequence

When an edge creation request is received:
1. Retrieve source node type (query Graph Store by `source_uid`)
2. Retrieve target node type (query Graph Store by `target_uid`)
3. Check Edge Validation Matrix for valid pairing `(source_node_type, edge_type, target_node_type)`
4. If invalid → return error `INVALID_EDGE_TYPE_PAIRING`
5. If valid → proceed with additional validation (state checks, cycle checks, etc.)

### Error Handling

**Error Code:** `INVALID_EDGE_TYPE_PAIRING`
**Error Message Format:** "Edge type '{edge_type}' cannot connect {source_node_type} → {target_node_type}. Valid target node types for {edge_type} from {source_node_type}: [list of valid types]."

**Example:**
```
Error: Edge type 'DERIVED_FROM' cannot connect Requirement → Constraint. 
Valid target node types for DERIVED_FROM from Requirement: [Requirement]
```

## 9. Relationship to Other Artifacts

### ICD-01 (Graph Ontology)

**Relationship:** Edge Validation Matrix extends ICD-01 with compatibility rules
- ICD-01 defines the structure (Node Types, Edge Types)
- Edge Validation Matrix defines the constraints (which combinations are valid)

### Workflow State Model

**Relationship:** Edge Validation Matrix may include state constraints
- Some edges may only be valid when nodes are in specific states (e.g., Approved)
- Workflow State Model defines state transitions
- Edge Validation Matrix may reference states (e.g., "DERIVED_FROM edges only valid when both nodes are Approved")

### Allocation Map

**Relationship:** Edge Validation Matrix identifies enforcement component
- The Governor (Constraint Rules module) enforces edge validation
- Allocation Map assigns responsibility to The Governor
- L3 requirements for The Governor reference the matrix

### L3 Requirements

**Relationship:** Edge Validation Matrix enables precise L3 specs
- L3 requirements for The Governor reference the matrix
- Validation logic is unambiguous (check matrix for valid pairing)
- Error handling is defined (specific error codes and messages)

## 10. Summary: The Value Proposition

An Edge Validation Matrix is essential because:

1. **Prevents Graph Corruption:** Blocks invalid edges at creation, maintaining graph semantic integrity
2. **Enables Precise L3 Requirements:** Provides unambiguous validation specification for component requirements
3. **Reduces Development Churn:** Freezes edge validation rules before implementation, preventing mid-development changes
4. **Ensures System Reliability:** Graph queries, constraint evaluation, and semantic inference work correctly with valid edges only

**Without it:** Graph corruption, ambiguous L3 requirements, implementation churn, broken semantic inference

**With it:** Graph integrity, precise L3 requirements, stable implementation, reliable system behavior
