To think through this via first principles, we need to strip away the "agile" or "waterfall" jargon and look at the fundamental engineering purpose of each level.

Here is the First Principles framework for L2 Requirements and how they are derived.

### 1. The Core First Principles of L2

If **L1** is the **Strategic Intent** (The "Why" and the "What"), **L2** is the **System Architecture & Constraints** (The "How").

#### Principle #1: Mechanism over Outcome
* **L1 (Outcome):** "The car must be fast." (This is a goal, not a design).
* **L2 (Mechanism):** "The powertrain must deliver 500HP," or "The chassis drag coefficient must be < 0.25."
* **The Principle:** L2 defines the **specific machinery or logic** required to achieve the L1 outcome. If you hand L2s to a developer, they know *what to build*, not just *what to hope for*.

#### Principle #2: The "MECE" Rule (Mutually Exclusive, Collectively Exhaustive)
* To derive L2s, you must ask: *"If I build all these L2s, is the L1 guaranteed to be fully met?"*
* **Collectively Exhaustive:** You haven't missed a piece of the puzzle.
* **Mutually Exclusive:** You don't have two requirements asking for the same thing in different words (this reduces "Noise").

#### Principle #3: Binary Verifiability (The "Signal")
* L1s are often qualitative ("Intuitive," "Robust," "Safe").
* L2s must be **binary** (Pass/Fail).
* **The Principle:** An L2 is not a sliding scale. It is a boundary. The system either *has* the specific node type, or it *doesn't*. It either *blocks* the conflict, or it *doesn't*.

### 2. The Derivation Process: "Decomposition via Necessity"

How do you actually move from L1 to L2? You don't just "brainstorm." You use a logical sieve.

**The Prompt:** *"What must be physically/logically true about the system for [L1] to exist?"*

Let's apply this to your **L1-REQ-1 (Connected Knowledge Graph)**.

#### Step 1: Isolate the Core Concepts in L1
Your L1 says: *"Store artifacts as **nodes**... support **multi-dimensional views**... capture **intent of relationships**."*

#### Step 2: Interrogate with "Necessity" (The Derivation)

| The "Why" (L1 Intent) | The Interrogation (Q) | The Derived "How" (L2 Mechanism) |
| :--- | :--- | :--- |
| **"Store artifacts as nodes"** | *Q: What kind of nodes? Do we allow users to create garbage nodes?* | **L2-REQ-1.1 (Ontology):** The system shall strictly enforce a fixed schema of Node Types (Req, Test, Component) and forbid generic "Item" nodes. |
| **"Capture intent of relationships"** | *Q: How do we distinguish a 'copy' from a 'trace'? How do we make it computable?* | **L2-REQ-1.2 (Typed Edges):** The system shall support only specific, directed Edge Types (Derived_From, Verified_By) and reject undefined links. |
| **"Support multi-dimensional views"** | *Q: How does the system know it's the same object in two different views?* | **L2-REQ-1.3 (Unique Identity):** Every node must be assigned a globally unique, immutable ID (UUID) that persists across all views and versions. |



### 3. Signal vs. Noise in L2 Derivation

For your MVP, you must filter L2 candidates through the "Signal" lens.

* **Noise L2 (Discard):** *"The system shall allow users to color-code nodes."*
    * *Why it's noise:* Color is visual. It helps the human eye, but the **Engine** (the computer) cannot calculate anything based on color.
* **Signal L2 (Keep):** *"The system shall prevent circular dependencies in `Derived_From` edges."*
    * *Why it's signal:* This is a logical constraint. If you don't build this, the Engine crashes.

### Summary: The Litmus Test
You know you have a good set of L2 requirements when:
1.  **Completeness:** If you implemented all of them, the L1 is 100% satisfied.
2.  **Independence:** You can assign L2-REQ-1.1 to Developer A and L2-REQ-1.2 to Developer B, and they can work (mostly) in parallel.
3.  **Testability:** You can write a script to verify it without asking a human "Do you like this?"
