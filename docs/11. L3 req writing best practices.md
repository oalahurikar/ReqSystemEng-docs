# L3 Requirements Writing: Component-Level Specifications

## Definition

**L3: Component Requirements (Black Box)**

L3 requirements describe the external behavior of one specific component (e.g., "The Motor Controller", "The Graph Engine", "The Governor").

**Focus:** Inputs, Outputs, and Performance. It does not say how the code works.

**Example:** "The Motor Controller shall accept a CAN message ID 0x100 and output 20A current within 10ms."

**Key Activity:** Allocation. You take an L2 System Requirement ("Drone shall hover") and slice it into L3 Requirements for the Battery, Motor, and Flight Computer.

---

## Best Practices

Emphasize **Allocation** and **Quantification**, which are the two places where L3s usually fail.

Here is the finalized **L3 Derivation & Writing Guide**, followed by the application to your specific L2 requirements.

-----

### 🏛️ The L3 Derivation Standard

**The Mental Model:**

  * **L1 (Goal):** "Win the race."
  * **L2 (Feature):** "The car must have a top speed of 200mph."
  * **L3 (Component Spec):** "The fuel pump shall deliver 500 liters/hr at 60psi." (Allocated, measurable, physics-based).

#### 1\. The "Meat Grinder" Process (Derivation)

Do not "brainstorm" L3s. Use this algorithmic process to decompose an L2.

1.  **Allocation (Who?):** Which specific *logical component* (Database, API, UI, Engine) is responsible for this?
      * *Rule:* An L3 cannot have "The System" as the subject. It must be "The Graph Engine" or "The Auth Service."
2.  **Decomposition (The Sequence):** Break the L2 feature into a chronological sequence of atomic steps.
      * *Input $\to$ Validate $\to$ Process $\to$ Store $\to$ Output.*
3.  **Quantification (The Metric):** Every adjective in L2 ("fast," "reliable") must become a number in L3.
      * *Rule:* No adverb is allowed without a number.
4.  **The "Rainy Day" (Negative Paths):** For every "Happy Path" L3, write at least one "Error State" L3.
      * *What happens if the input is null? If the DB is down? If the user has no permission?*

#### 2\. The INCOSE/EARS "Syntax Constraints"

Strictly enforce these rules for L3 text:

| Rule | Constraint | Bad Example | Good Example |
| :--- | :--- | :--- | :--- |
| **Singularity** | One verb per requirement. | "Calculate **and** display." | **Req A:** "Calculate..." <br> **Req B:** "Display..." |
| **Black Box** | Describe *observable behavior*, not internal code. | "Use an SQL Join to find..." | "Retrieve all records where..." |
| **Universality** | Use the EARS patterns strictly. | "The system should try to..." | **Event-driven:** "When [trigger], the [component] shall..." |
| **Isolation** | No external dependencies in the text. | "As described in the Jira ticket..." | (Self-contained definition) |

### 🚀 Application: Deriving L3s for your L2 Requirements

Let's take your two critical L2s (**L2-REQ-1.2 Ontology** and **L2-REQ-1.7 Serialization**) and drive them down to L3.

#### Example 1: The Ontology (L2-REQ-1.2)

**Parent L2:** *The system shall enforce a strict, limited set of Node Types... mapping 1:1 to SysML v2... rejecting undefined types.*

**Component Allocation:** `Graph Database Schema` (The "Governor")

| ID | EARS Pattern | L3 Requirement Text | Verification |
| :--- | :--- | :--- | :--- |
| **L3-REQ-1.2.1** | **Ubiquitous** | The Graph Schema shall define exactly four immutable Node Types: `Requirement`, `TestCase`, `Component`, and `Parameter`. | **Inspection:** Schema definition file contains only these 4 enums. |
| **L3-REQ-1.2.2** | **Ubiquitous** | The Graph Schema shall include a metadata property `sysml_mapping` for each Node Type, containing the valid SysML v2 KerML class name (e.g., `RequirementUsage`). | **Inspection:** DB Schema check. |
| **L3-REQ-1.2.3** | **Unwanted** | If a `CreateNode` request contains a `type` string not matching the defined four types, the API shall return an `HTTP 400 Bad Request` error with code `INVALID_NODE_TYPE`. | **Test:** API Integration Test (Negative). |
| **L3-REQ-1.2.4** | **State-Driven** | While a node exists in the database, the Graph Engine shall prevent any modification to its `type` property (making identity immutable). | **Test:** Attempt `PATCH /node/{id} {type: "new"}` $\to$ Expect Error. |

**Critique:**

  * **Precise Subject:** "Graph Schema" / "API" (not just "System").
  * **Measurable:** HTTP 400, specific error code.
  * **Complete:** Covers the Definition, the Mapping, the Error Case, and the Immutability.

#### Example 2: The Serialization (L2-REQ-1.7)

**Parent L2:** *The system shall provide a deterministic mechanism to serialize... into structured text (Markdown/SysML)... optimized for LLM.*

**Component Allocation:** `Context Serializer Service` (The "Translator")

| ID | EARS Pattern | L3 Requirement Text | Verification |
| :--- | :--- | :--- | :--- |
| **L3-REQ-1.7.1** | **Event-Driven** | When a serialization request specifies `format='sysml'`, the Serializer shall generate a text string conforming to the **SysML v2 Textual Notation** grammar for the target node and its edges. | **Test:** Parse output with standard SysML v2 parser; expect 0 syntax errors. |
| **L3-REQ-1.7.2** | **Event-Driven** | When a serialization request specifies `depth=N`, the Serializer shall traverse the graph to exactly **N hops** from the source node and include all visited nodes/edges in the output. | **Test:** Create chain A-B-C. Request depth=1. Verify output has A, B, but not C. |
| **L3-REQ-1.7.3** | **Ubiquitous** | The Serializer shall sort all edges and child nodes in the output alphanumerically by `UID` to guarantee deterministic output for identical graph states. | **Test:** Call serialize() 100 times. Hash the output. Expect 1 unique hash. |
| **L3-REQ-1.7.4** | **Unwanted** | If the serialization traversal exceeds a token budget of **8,000 tokens** (configurable), the Serializer shall truncate the output at the nearest complete node boundary and append a `[TRUNCATED]` footer. | **Test:** Create massive graph. Request serialize. Verify output length \< limit and footer presence. |

**Critique:**

  * **Quantified:** "8,000 tokens," "N hops."
  * **Deterministic:** L3-REQ-1.7.3 explicitly forces sorting (crucial for LLM caching).
  * **Standard-Compliant:** L3-REQ-1.7.1 references the "SysML v2 Grammar" standard.
