# Allocation Map: Purpose, Timing, and Value
**First Principles & Best Practices**

---

## 1. First Principles: The Physics of Allocation

An Allocation Map is not "documentation." It is a **Contract** that assigns behavioral responsibilities to architectural components, establishing single ownership for each requirement.

* **The Principle of Ownership:** Every behavior must have exactly one component responsible. If ownership is unclear, the architecture is incomplete or ambiguous.
* **The Principle of Decomposition:** You cannot write valid L3 (Component) requirements without knowing which component is responsible. Allocation is the bridge between L2 (System Feature) and L3 (Component Spec).
* **The Principle of Traceability:** Allocation enables implementation traceability: L1 → L2 → Component → Code. Without allocation, you cannot answer "Where is this requirement implemented?"

---

## 2. Purpose & When to Use

### What is an Allocation Map?

A single-page table that maps each L1/L2 requirement to **exactly one architecture component** responsible for implementing it. Example:

> "Blocks invalid state transitions" → **The Governor** (State Machine module)

### When to Create It

**Timing:** After L2 requirements are complete, but **before** L3 decomposition begins.

**Process Stage:**
1. ✅ L1 Requirements defined (Strategic Intent)
2. ✅ L2 Requirements derived (System Features/Mechanisms)
3. ✅ Architecture components defined (from System Architecture document)
4. 🎯 **ALLOCATION MAP CREATED** ← You are here
5. ⏭️ L3 Requirements decomposed (Component Specs with allocation)

**Why This Order Matters:**
- You need L2 requirements to know what behaviors to allocate
- You need architecture components to know what components exist
- You cannot write L3 requirements without knowing which component is responsible (L3 format requires "Allocated Component" field)

---

## 3. Value Added

### 1. Enables Proper L3 Decomposition

**Without Allocation:** L3 requirements are vague ("The system shall...") or miss the component entirely.

**With Allocation:** L3 requirements are precise ("The Governor shall...") and testable at the component level.

**Example:**
- ❌ Bad L3: "The system shall block invalid state transitions."
- ✅ Good L3: "The Governor (State Machine module) shall reject state transitions from Approved → Draft."

### 2. Prevents Architectural Gaps

**Gap Detection:** If a requirement cannot be allocated to any existing component, you have an architectural gap. This triggers:
- Architecture refinement (add missing component)
- Requirement revision (requirement is too vague or out of scope)

**Example:** If L2-REQ-7.2 (Conflict Blocking) cannot be allocated, you're missing the enforcement mechanism in your architecture.

### 3. Clarifies Component Responsibilities

**Single Ownership:** Each requirement has exactly one owner. This prevents:
- Duplication (two components implementing the same behavior)
- Gaps (no component responsible)
- Ambiguity (unclear who owns the behavior)

**Example:** L2-REQ-1.7 (Graph Serialization) is allocated to Context Serializer, not Graph Store. This clarifies that serialization is a separate concern from storage.

### 4. Enables Implementation Traceability

**Traceability Chain:** L1 → L2 → Component → Code

**Without Allocation:** Cannot trace requirements to code. Developer asks "Where do I implement L1-REQ-7?" and gets silence.

**With Allocation:** Clear path: L1-REQ-7 → L2-REQ-7.2 → The Governor (Constraint Rules module) → `governor/constraint_rules.py:block_violation()`

### 5. Supports Systems Engineering Best Practices

**INCOSE Standard:** Requirement allocation is a standard systems engineering practice. It aligns with:
- Modularity (clear component boundaries)
- Separation of concerns (each component has distinct responsibilities)
- Verification planning (component-level testing requires component-level requirements)

## 4. Without It - The Consequences

### Problem 1: L3 Requirements Cannot Be Written

**Symptom:** L3 requirements are vague or miss the component allocation.

**Impact:** Developers don't know which component to implement. Requirements become untestable at the component level.

**Example:**
- Without allocation: "The system shall evaluate constraints against requirements."
- Developer asks: "Where? In the API Gateway? In the Governor? In the Graph Store?"
- Result: Implementation delays, architectural confusion, testing gaps.

### Problem 2: Architectural Gaps Go Undetected

**Symptom:** Requirements cannot be allocated to any component.

**Impact:** Missing components are discovered late, requiring architecture rework.

**Example:**
- L2-REQ-7.1 (Constraint Evaluation) requires unit normalization logic.
- No component owns "unit conversion" behavior.
- Discovered during implementation: "Wait, where does unit conversion happen?"
- Result: Late architecture change, component reallocation, implementation rework.

### Problem 3: Duplication and Overlap

**Symptom:** Multiple components claim ownership of the same behavior.

**Impact:** Code duplication, inconsistent implementations, maintenance burden.

**Example:**
- Both API Gateway and The Governor implement permission checks.
- Result: Two codebases to maintain, potential inconsistencies, security gaps.

### Problem 4: No Implementation Traceability

**Symptom:** Cannot trace requirements to code.

**Impact:** 
- Code reviews cannot verify requirement implementation
- Testing cannot verify component-level requirements
- Changes cannot assess requirement impact

**Example:**
- Developer modifies `graph_store.py` but doesn't know which requirements are affected.
- Result: Unintended requirement violations, regression bugs, testing gaps.

### Problem 5: Fuzzy Boundaries Lead to Arguments

**Symptom:** Unclear ownership leads to team arguments during implementation.

**Impact:** Delays, rework, frustration.

**Example:**
- L2-REQ-6.3 (Real-Time Guidance) is not allocated.
- Team argues: "Should LLM Orchestrator compute guidance, or should Streamlit Chat do it?"
- Result: Design arguments during sprint planning, implementation delays.

**Solution:** Fuzzy allocations are **documented as "Notes"** in the Allocation Map. They become **L3 design arguments** where interface contracts and interaction patterns are precisely defined.

## 5. How to Create an Allocation Map

### Step 1: List All Requirements

- Extract all L1 requirements from `requirements/L1_MVP.md`
- Extract all L2 requirements from `requirements/L2/` directory

### Step 2: List All Architecture Components

- Extract components from `docs/System Architecture.md`
- Include component modules (e.g., "The Governor (State Machine module)")

### Step 3: Allocate Each Requirement

**Allocation Rules:**
1. **Single Owner:** Each requirement has exactly one component responsible
2. **Component Exists:** Only allocate to components defined in System Architecture
3. **Behavior Fits:** Component's responsibilities (from System Architecture) must align with requirement behavior
4. **Mark Fuzzy:** If ownership is unclear, document in "Notes" section for L3 resolution

**Allocation Logic:**
- Use System Architecture component descriptions to match responsibilities
- Use L2 requirement "Derived From" to understand parent-child relationships
- Use System Architecture "L2 Traceability" sections to see existing allocations

### Step 4: Document Fuzzy Allocations

**What is "Fuzzy"?**
- Requirement requires coordination between multiple components
- Component ownership is unclear (architecture gap)
- Interface contracts are undefined (L3 will define them)

**How to Handle:**
- Document in "Notes on Fuzzy Allocations" section
- Explain the coordination needed
- Note that L3 decomposition will resolve with interface contracts

### Step 5: Validate Completeness

**Checklist:**
- ✅ Every L1 requirement allocated (or marked fuzzy)
- ✅ Every L2 requirement allocated (or marked fuzzy)
- ✅ Every allocation references a component from System Architecture
- ✅ No component is assigned requirements outside its responsibilities (from System Architecture)

## 6. Allocation Map Format

### Table Structure

**L1 Requirements Allocation:**
| L1 Requirement | Allocated Component | Rationale |

**L2 Requirements Allocation:**
| L2 Requirement | Allocated Component | Rationale |

### Rationale Column

**Purpose:** Explain why this allocation was chosen.

**Good Rationale:**
- "Backend-level blocking enforcement (cannot bypass via API)"
- "Core graph data model and storage mechanism"
- "Real-time ambiguity detection and verifiability checking"

**Bad Rationale:**
- "Because it makes sense"
- "This component needs to do something"
- (Empty rationale)

### Notes Section

**What to Include:**
- Fuzzy allocations requiring L3 resolution
- Coordination patterns between components
- Interface contracts to be defined in L3

---

## 7. Relationship to Other Artifacts

### Inputs to Allocation Map

- **L1 Requirements:** Strategic intent (from `requirements/L1_MVP.md`)
- **L2 Requirements:** System features/mechanisms (from `requirements/L2/`)
- **System Architecture:** Component catalog and responsibilities (from `docs/System Architecture.md`)

### Outputs from Allocation Map

- **L3 Requirements:** Component-level specs with "Allocated Component" field
- **Interface Contracts (ICDs):** Contracts between components for fuzzy allocations
- **Verification Plans:** Component-level test requirements

---

## Summary

The Allocation Map is a **critical bridge** between system-level requirements (L2) and component-level requirements (L3). Without it:

- ❌ L3 requirements are vague or incomplete
- ❌ Architectural gaps go undetected
- ❌ Implementation traceability is broken
- ❌ Design arguments delay implementation

With it:

- ✅ Clear component ownership for every behavior
- ✅ Proper L3 decomposition with component allocation
- ✅ Implementation traceability: Requirement → Component → Code
- ✅ Fuzzy allocations documented for L3 resolution

**Create it after L2, before L3. It's not optional—it's a systems engineering best practice.**
