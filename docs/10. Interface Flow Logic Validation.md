# Interface Flow Logic Validation: Contract Enforcement
**First Principles & Best Practices**

---

## 1. First Principles: The Physics of Contract Validation

Interface Flow Logic Validation is not "testing." It is **Contract Enforcement** that validates Producer and Consumer agree on the ICD contract before data flows between components.

* **The Principle of Agreement:** An ICD defines the contract, but L3 must define what makes the contract "valid" when data flows. Schema validation (structure) is not enough—you need contract validation (compatibility).
* **The Principle of Bidirectional Validation:** Both Producer and Consumer must validate the contract. Producer validates it's sending valid data; Consumer validates it's receiving expected data.
* **The Principle of Fail-Fast:** Contract violations must be detected immediately at the interface boundary, not deep inside component logic.

---

## 2. What is Interface Flow Logic Validation?

### Schema Validation vs. Contract Validation

**Schema Validation (What We Have):**
- Validates data structure matches Pydantic model
- Checks field types, constraints, enums
- Example: "Is this `IngestionPacket` correctly structured?"

**Contract Validation (What You Need):**
- Validates Producer output matches Consumer input expectations
- Checks unit compatibility, frequency matching, data format compatibility
- Example: "When Input Parser sends `IngestionPacket` to Graph Builder, does Graph Builder correctly understand and process it?"

### The Gap

Your ICDs define:
- ✅ **Producer:** Who sends the data
- ✅ **Consumer:** Who receives the data
- ✅ **Schema:** What the data structure looks like

But they don't define:
- ❌ **Validation Logic:** How Consumer validates it received correct data
- ❌ **Compatibility Rules:** Unit matching, frequency matching, format compatibility
- ❌ **Error Handling:** What happens when contract is violated

---

## 3. When to Define Contract Validation

**Timing:** After ICDs are defined, but **before** L3 component implementation begins.

**Process Stage:**
1. ✅ ICDs defined (data contracts)
2. ✅ Allocation Map created (component responsibilities)
3. 🎯 **CONTRACT VALIDATION LOGIC DEFINED** ← You are here
4. ⏭️ L3 Requirements written (component specs with validation logic)

**Why This Order Matters:**
- You need ICDs to know what contracts exist
- You need Allocation Map to know which components are Producer/Consumer
- You cannot write L3 requirements without knowing how to validate contracts
- L3 requirements must specify validation logic for each interface

## 4. What Makes a Handshake "Valid"?

### Validation Dimensions

For each ICD contract, L3 must define validation rules for:

#### 1. **Schema Compatibility**
- Does Producer output match Consumer input schema?
- Are all required fields present?
- Are field types compatible?

**Example (ICD-02):**
```python
# Producer: Input Parser sends IngestionPacket
# Consumer: Graph Builder receives it

# L3 Validation Rule:
# "Graph Builder shall validate that IngestionPacket.candidates 
#  list contains at least one Candidate with confidence > 0.5"
```

#### 2. **Unit Compatibility**
- Do units match between Producer and Consumer?
- Is unit conversion required?
- Are units dimensionally compatible?

**Example (Physical Interface):**
```python
# Producer: Flight Controller sends "Torque = 100 Nm"
# Consumer: Motor expects "Torque in Nm"

# L3 Validation Rule:
# "Motor shall validate that received torque unit is 'Nm'. 
#  If unit mismatch detected, reject command and return error code UNIT_MISMATCH"
```

#### 3. **Frequency/Timing Compatibility**
- Does update frequency match expectations?
- Is timing within acceptable bounds?
- Are there timing constraints?

**Example:**
```python
# Producer: Sensor sends data at 50Hz
# Consumer: Controller expects data at 50Hz

# L3 Validation Rule:
# "Controller shall validate that sensor data arrives at 50Hz ± 5Hz. 
#  If frequency deviation > 5Hz, log warning and use last valid value"
```

#### 4. **Data Format Compatibility**
- Does data format match expected format?
- Are encodings compatible?
- Are serialization formats compatible?

**Example (ICD-05):**
```python
# Producer: Context Serializer sends SerializedContext with format='markdown'
# Consumer: LLM Orchestrator expects format='markdown' or 'sysml_v2'

# L3 Validation Rule:
# "LLM Orchestrator shall validate that SerializedContext.format 
#  is either 'markdown' or 'sysml_v2'. If invalid format, reject and request re-serialization"
```

#### 5. **Value Range Compatibility**
- Are values within acceptable ranges?
- Do min/max constraints match?
- Are value types compatible?

**Example:**
```python
# Producer: Sends confidence score 0.95
# Consumer: Expects confidence in range [0.0, 1.0]

# L3 Validation Rule:
# "Graph Builder shall validate that Candidate.confidence 
#  is within bounds [0.0, 1.0]. If out of bounds, reject packet"
```

## 5. How to Write L3 Contract Validation Requirements

### Format for L3 Contract Validation Requirements

Each ICD contract needs L3 requirements that specify validation logic:

```markdown
**L3-REQ-X.X: [Component] ICD-[XX] Contract Validation**

**Allocated Component:** [Consumer Component]
**ICD Contract:** ICD-XX (Producer → Consumer)

**WHAT:**
When [Consumer Component] receives [ICD Model] from [Producer Component], 
the [Consumer Component] shall validate:
1. [Validation Rule 1: Schema compatibility]
2. [Validation Rule 2: Unit compatibility]
3. [Validation Rule 3: Frequency/timing compatibility]
4. [Validation Rule 4: Format compatibility]
5. [Validation Rule 5: Value range compatibility]

**Error Handling:**
If validation fails, the [Consumer Component] shall:
- Reject the [ICD Model]
- Return error code [ERROR_CODE]
- Log contract violation with details [what details]

**EARS Pattern:** [Event-Driven: "When [ICD Model] received..."]
```

### Example: ICD-02 Contract Validation

```markdown
**L3-REQ-2.1: Graph Builder ICD-02 Contract Validation**

**Allocated Component:** Graph Builder (Graph Store)
**ICD Contract:** ICD-02 (Input Parser → Graph Builder)

**WHAT:**
When Graph Builder receives an IngestionPacket from Input Parser, 
the Graph Builder shall validate:
1. **Schema Compatibility:** All Candidate objects have valid implied_type (NodeType enum)
2. **Value Range:** All Candidate.confidence values are within [0.0, 1.0]
3. **Data Completeness:** IngestionPacket.source_id is not empty
4. **List Constraints:** IngestionPacket.candidates list contains at least one Candidate

**Error Handling:**
If validation fails, the Graph Builder shall:
- Reject the IngestionPacket
- Return error code `ICD_02_VALIDATION_FAILED`
- Log contract violation with details: field_name, expected_value, actual_value

**EARS Pattern:** Event-Driven: "When IngestionPacket received from Input Parser..."
```

### Example: ICD-03 Contract Validation

```markdown
**L3-REQ-3.1: Frontend ICD-03 Contract Validation**

**Allocated Component:** Streamlit Chat (Frontend)
**ICD Contract:** ICD-03 (Guidance Engine → Frontend)

**WHAT:**
When Frontend receives a GuidanceResult from Guidance Engine, 
the Frontend shall validate:
1. **Schema Compatibility:** GuidanceResult contains all required nested models (ambiguity, verifiability, relationships)
2. **Data Completeness:** GuidanceResult.node_uid is not empty
3. **Timestamp Validity:** GuidanceResult.timestamp is within last 5 seconds (real-time constraint)

**Error Handling:**
If validation fails, the Frontend shall:
- Ignore the GuidanceResult (don't display)
- Log warning: "Stale or invalid guidance result received"
- Continue with previous guidance state

**EARS Pattern:** Event-Driven: "When GuidanceResult received from Guidance Engine..."
```

## 6. Contract Testing Strategy

### Integration Tests for Contract Validation

Create integration tests that validate Producer/Consumer compatibility:

```python
# tests/integration/test_icd_02_contract.py

def test_icd_02_producer_consumer_compatibility():
    """Validate Input Parser output matches Graph Builder input expectations."""
    # 1. Input Parser creates IngestionPacket
    packet = input_parser.parse("The motor shall deliver torque < 100 Nm")
    
    # 2. Graph Builder validates packet
    result = graph_builder.validate_ingestion_packet(packet)
    
    # 3. Verify contract is honored
    assert result.is_valid == True
    assert result.error_code is None

def test_icd_02_unit_compatibility():
    """Validate units match between Producer and Consumer."""
    # Producer sends parameter with unit "Nm"
    packet = create_packet_with_parameter(unit="Nm")
    
    # Consumer validates unit
    result = graph_builder.validate_ingestion_packet(packet)
    
    # Verify unit is accepted
    assert result.is_valid == True

def test_icd_02_contract_violation():
    """Validate contract violation is detected and handled."""
    # Producer sends invalid packet (confidence > 1.0)
    packet = create_packet_with_invalid_confidence(confidence=1.5)
    
    # Consumer rejects packet
    result = graph_builder.validate_ingestion_packet(packet)
    
    # Verify rejection
    assert result.is_valid == False
    assert result.error_code == "ICD_02_VALIDATION_FAILED"
    assert "confidence" in result.violation_details
```

## 8. Common Validation Patterns

### Pattern 1: Schema Validation
```python
# L3 Requirement:
# "Component shall validate that received data matches ICD schema"

# Implementation:
try:
    packet = IngestionPacket(**data)
except ValidationError as e:
    return ContractValidationResult(
        is_valid=False,
        error_code="SCHEMA_MISMATCH",
        details=str(e)
    )
```

### Pattern 2: Unit Compatibility
```python
# L3 Requirement:
# "Component shall validate that units match expected units"

# Implementation:
if received_unit != expected_unit:
    # Check if units are dimensionally compatible
    if not are_units_compatible(received_unit, expected_unit):
        return ContractValidationResult(
            is_valid=False,
            error_code="UNIT_MISMATCH",
            details=f"Expected {expected_unit}, received {received_unit}"
        )
    # Convert units if compatible
    converted_value = convert_units(value, received_unit, expected_unit)
```

### Pattern 3: Frequency Validation
```python
# L3 Requirement:
# "Component shall validate that data arrives at expected frequency"

# Implementation:
current_time = time.now()
time_since_last = current_time - last_received_time
expected_interval = 1.0 / expected_frequency

if abs(time_since_last - expected_interval) > tolerance:
    return ContractValidationResult(
        is_valid=False,
        error_code="FREQUENCY_MISMATCH",
        details=f"Expected {expected_frequency}Hz, actual {1.0/time_since_last}Hz"
    )
```

### Pattern 4: Value Range Validation
```python
# L3 Requirement:
# "Component shall validate that values are within acceptable ranges"

# Implementation:
if value < min_value or value > max_value:
    return ContractValidationResult(
        is_valid=False,
        error_code="VALUE_OUT_OF_RANGE",
        details=f"Value {value} outside range [{min_value}, {max_value}]"
    )
```

## 9. Validation Checklist for Each ICD

For each ICD contract, ensure L3 requirements define:

- [ ] **Schema Compatibility:** Producer output matches Consumer input schema
- [ ] **Unit Compatibility:** Units match or are dimensionally compatible
- [ ] **Frequency/Timing:** Update frequency matches expectations (if applicable)
- [ ] **Format Compatibility:** Data format matches expected format
- [ ] **Value Range:** Values within acceptable bounds
- [ ] **Error Handling:** Contract violation detection and reporting
- [ ] **Integration Tests:** Tests that validate Producer/Consumer compatibility

---

## 10. Summary

Interface Flow Logic Validation is the **missing link** between ICD definitions (the contract) and L3 component requirements (the implementation).

**Without Contract Validation:**
- ❌ Components may send/receive incompatible data
- ❌ Unit mismatches cause silent failures
- ❌ Integration issues discovered late
- ❌ No clear error handling for contract violations

**With Contract Validation:**
- ✅ L3 requirements specify validation logic
- ✅ Integration tests validate Producer/Consumer compatibility
- ✅ Contract violations detected immediately
- ✅ Clear error handling and reporting

**The tests we created (schema validation) are Step 1.**  
**Contract validation (L3 requirements) is Step 2.**  
**Integration tests (Producer/Consumer compatibility) is Step 3.**

All three are needed for complete Interface Flow Logic Validation.
