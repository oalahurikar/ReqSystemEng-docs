# Workflow/State Model: State Transition Rules
**First Principles & Best Practices**

---

## 1. First Principles: The Physics of State Transitions

A Workflow/State Model is not "documentation." It is a **Decision Table** that defines the exact conditions, guard rules, and error handling for state transitions, enabling precise L3 component requirements.

* **The Principle of Determinism:** Every state transition must be deterministic. Given the same input conditions, the system must always produce the same result (transition allowed or blocked).
* **The Principle of Guard Conditions:** State transitions are not automatic—they require explicit guard conditions to be met. If any guard fails, the transition is blocked with a specific error.
* **The Principle of Fail-Fast:** Invalid state transitions must be detected and blocked immediately at the boundary (The Governor), not deep inside component logic.

---

## 2. What is a Workflow/State Model?

### Definition

A Workflow/State Model defines:
- **States:** All valid states a requirement can be in (e.g., Draft, Approved)
- **Transitions:** Allowed state transitions (e.g., Draft → Approved)
- **Guard Conditions:** Rules that must be satisfied before a transition is allowed
- **Blocked Paths:** Conditions that prevent transitions (with specific error codes)
- **Entry/Exit Actions:** What happens when entering or exiting a state
- **Sequence:** The order in which guard conditions are evaluated

### Schema Validation vs. State Transition Validation

**Schema Validation (What We Have):**
- Validates data structure matches Pydantic model
- Checks field types, constraints, enums
- Example: "Is this requirement node correctly structured?"

**State Transition Validation (What You Need):**
- Validates guard conditions before allowing state change
- Checks permissions, quality gates, completeness
- Example: "Can this Draft requirement transition to Approved? Check: permission → quality gate → completeness → transition allowed/blocked"

### The Gap

Your L2 Requirements define:
- ✅ **States:** Draft, Approved (L2-REQ-2.1)
- ✅ **Transition:** Draft → Approved (one-way, L2-REQ-2.1)
- ✅ **Blocking conditions:** Quality gate (L2-REQ-6.4), Draft usage (L2-REQ-2.4)

But they don't define:
- ❌ **Guard Condition Sequence:** Order of checks (permission → quality → completeness)
- ❌ **Error Handling:** Specific error codes for each failure mode
- ❌ **Entry/Exit Actions:** What happens when state changes (logging, notifications, side effects)

## 3. Why Use a Workflow/State Model?

### 1. Enables Precise L3 Requirements

**Without Workflow/State Model:**
- L3 requirements are vague: "System shall block invalid state transitions"
- Unclear order of operations: Should permission check happen before or after quality gate?
- Missing error handling: What error code when approval blocked?

**With Workflow/State Model:**
- L3 requirements are precise: "The Governor shall validate guard conditions in sequence: (1) permission, (2) quality gate, (3) completeness. If any guard fails, return specific error code."
- Clear sequence: Permission check → Quality gate → Completeness check → Transition
- Defined error codes: `PERMISSION_DENIED`, `QUALITY_GATE_FAILED`, `INCOMPLETE_REQUIREMENT`

**Example L3 Requirement (with Workflow/State Model):**
```markdown
**L3-REQ-2.1.1: Draft → Approved Transition Guard Conditions**

**Allocated Component:** The Governor (State Machine module)
**Workflow/State Model Reference:** Section 4.2 (Draft → Approved Transition)

**WHAT:**
When a state transition request is received (Draft → Approved), The Governor shall:
1. Validate user role (must be Reviewer or Admin) → If fail, return `PERMISSION_DENIED`
2. Validate quality gate (no ambiguous terms, verifiable criteria present) → If fail, return `QUALITY_GATE_FAILED`
3. Validate completeness (requirement has non-empty content) → If fail, return `INCOMPLETE_REQUIREMENT`
4. If all guards pass → transition to Approved state, log transition event

**EARS Pattern:** Event-Driven: "When state transition request received..."
```

### 2. Prevents Ambiguity in Implementation

**Gap Detection:** If guard conditions are unclear or missing, implementation becomes ambiguous:
- Different developers implement different sequences
- Error handling is inconsistent
- Edge cases are missed (what if permission check passes but quality gate fails mid-check?)

**Example:** Without explicit sequence, one developer might check permission first, another might check quality gate first. This creates inconsistent behavior and makes debugging difficult.

### 3. Enables Integration Testing

With a Workflow/State Model, you can write comprehensive integration tests:

```python
def test_draft_to_approved_happy_path():
    """Validate Draft → Approved transition with all guards passing."""
    # Setup: Create Draft requirement, user with Reviewer role, quality checks pass
    requirement = create_draft_requirement(content="Motor torque < 100Nm")
    user = create_user(role="Reviewer")
    
    # Execute: Request approval
    result = governor.transition_state(requirement.uid, "Approved", user)
    
    # Verify: Transition succeeds
    assert result.is_allowed == True
    assert result.new_state == "Approved"

def test_draft_to_approved_permission_blocked():
    """Validate Draft → Approved blocked by permission guard."""
    # Setup: Create Draft requirement, user with Engineer role (no approval permission)
    requirement = create_draft_requirement(content="Motor torque < 100Nm")
    user = create_user(role="Engineer")
    
    # Execute: Request approval
    result = governor.transition_state(requirement.uid, "Approved", user)
    
    # Verify: Transition blocked with specific error
    assert result.is_allowed == False
    assert result.error_code == "PERMISSION_DENIED"
    assert result.error_message == "User role does not have approval permission"

def test_draft_to_approved_quality_gate_blocked():
    """Validate Draft → Approved blocked by quality gate."""
    # Setup: Create Draft requirement with ambiguous terms
    requirement = create_draft_requirement(content="The system shall be fast")
    user = create_user(role="Reviewer")
    
    # Execute: Request approval
    result = governor.transition_state(requirement.uid, "Approved", user)
    
    # Verify: Transition blocked with quality gate error
    assert result.is_allowed == False
    assert result.error_code == "QUALITY_GATE_FAILED"
    assert "ambiguous terms" in result.error_message.lower()
```

### 4. Provides Clear Error Handling Specification

**Error Taxonomy:** The Workflow/State Model defines a complete error taxonomy:
- Error codes for each failure mode
- Error messages that are user-friendly and actionable
- Error categories for proper handling (blocking vs. warning)

**Without Error Taxonomy:** Developers invent error codes inconsistently, making error handling and debugging difficult.

**With Error Taxonomy:** All components use the same error codes, enabling consistent error handling and better user experience.

## 4. When to Define Workflow/State Model

**Timing:** After L2 requirements define state behavior, but **before** L3 component requirements are written.

**Process Stage:**
1. ✅ L2 Requirements defined (state behavior specified: L2-REQ-2.1, 2.4, 6.4)
2. ✅ Allocation Map created (component ownership: The Governor owns state transitions)
3. 🎯 **WORKFLOW/STATE MODEL DEFINED** ← You are here
4. ⏭️ L3 Requirements written (component specs with guard conditions)

**Why This Order Matters:**
- You need L2 requirements to know what states and transitions exist
- You need Allocation Map to know which component owns state transitions (The Governor)
- You cannot write L3 requirements without knowing guard condition sequence and error handling
- L3 requirements must specify the exact implementation of state transition logic

## 5. How to Create a Workflow/State Model

### Step 1: Define States

List all valid states for requirements:

| State | Description | Can Be Used In Validation? | Source Requirement |
|-------|-------------|----------------------------|-------------------|
| **Draft** | Requirement is being created/edited, not yet validated | ❌ No | L2-REQ-2.1 |
| **Approved** | Requirement has passed review workflow | ✅ Yes | L2-REQ-2.1 |

**MVP States (Current):**
- Draft
- Approved

**Future States (Not in MVP, but document for evolution):**
- Pending Governor (intermediate state during approval process)
- Quarantined (blocked due to conflicts or quality issues)

### Step 2: Define Transitions

List all allowed state transitions:

| From State | To State | Direction | Irreversible? | Source Requirement |
|------------|----------|-----------|---------------|-------------------|
| Draft | Approved | One-way | ✅ Yes (MVP) | L2-REQ-2.1 |

**Invalid Transitions:**
- Approved → Draft: Not allowed (breaks traceability, L2-REQ-2.1)

### Step 3: Define Guard Conditions

For each transition, define the guard conditions that must pass:

**Draft → Approved Guard Conditions:**

| Guard # | Guard Condition | Validation Logic | Error Code (if fails) | Source Requirement |
|---------|----------------|------------------|----------------------|-------------------|
| 1 | Permission Check | User role must be Reviewer or Admin | `PERMISSION_DENIED` | L1-REQ-3 (RBAC) |
| 2 | Quality Gate | No ambiguous terms, verifiable criteria present | `QUALITY_GATE_FAILED` | L2-REQ-6.4 |
| 3 | Completeness | Requirement content is non-empty | `INCOMPLETE_REQUIREMENT` | L2-REQ-2.2 |

**Guard Condition Sequence:**
1. Permission Check (fastest check, fail early)
2. Quality Gate (requires LLM call, slower)
3. Completeness (fast validation, final check)

**Rationale for Sequence:**
- Permission check is fastest (in-memory role lookup)
- Quality gate is slowest (LLM API call), so check after permission (don't waste API calls for unauthorized users)
- Completeness is fast (string validation), final check before transition

### Step 4: Define Blocked Paths (Error Conditions)

For each guard condition, define the error response:

| Error Code | Error Message | Guard Condition | User Action |
|------------|---------------|-----------------|-------------|
| `PERMISSION_DENIED` | "User role does not have approval permission. Reviewer or Admin role required." | Permission Check fails | User must request approval from Reviewer/Admin |
| `QUALITY_GATE_FAILED` | "Requirement cannot be approved: [list of quality issues]. Resolve issues before approval." | Quality Gate fails | User must fix ambiguous terms or add verifiable criteria |
| `INCOMPLETE_REQUIREMENT` | "Requirement content is empty. Add content before approval." | Completeness check fails | User must add requirement content |

### Step 5: Define Sequence Diagram (The "Write Path")

Document the exact sequence of operations:

```
User Request: Approve Requirement (Draft → Approved)
    ↓
[Governor Receives Request]
    ↓
[Guard 1: Permission Check]
    ├─ Call: Permission Engine.check_permission(user, "approve_requirement")
    ├─ FAIL → Return Error: PERMISSION_DENIED
    └─ PASS → Continue
    ↓
[Guard 2: Quality Gate Check]
    ├─ Call: LLM Orchestrator.check_quality(requirement.content)
    ├─ Check: No ambiguous terms (L2-REQ-6.1)
    ├─ Check: Verifiable criteria present (L2-REQ-6.2)
    ├─ FAIL → Return Error: QUALITY_GATE_FAILED (with list of issues)
    └─ PASS → Continue
    ↓
[Guard 3: Completeness Check]
    ├─ Check: requirement.content is not empty
    ├─ Check: requirement.content.strip() has length > 0
    ├─ FAIL → Return Error: INCOMPLETE_REQUIREMENT
    └─ PASS → Continue
    ↓
[All Guards Pass - Execute Transition]
    ├─ Update: Graph Store.update_node(requirement.uid, status="Approved")
    ├─ Log: Transition event (from_state="Draft", to_state="Approved", user=user.uid, timestamp=now())
    ├─ Trigger: Async event to update Vector Store embeddings
    └─ Return: SUCCESS (new_state="Approved")
```

### Step 6: Define Entry/Exit Actions

Specify what happens when entering or exiting a state:

**Entering Approved State (Exit Draft):**
- Update node.status property in Graph Store
- Log transition event (for audit trail)
- Trigger async event to update Vector Store embeddings (L1-REQ-8)
- Notify dependent requirements (if any) that parent is now Approved

**Exiting Draft State (Enter Approved):**
- Clear any quality flags (ambiguity warnings, verifiability warnings)
- Enable requirement for use in validation operations (L1-REQ-7, L1-REQ-8, L1-REQ-9)

### Step 7: Define State Usage Rules

Specify what operations are allowed in each state:

**Draft State:**
- ✅ Create, Read, Update, Delete (with permission checks)
- ✅ Quality guidance (L1-REQ-6) - real-time feedback
- ❌ Cannot be used in validation operations (L2-REQ-2.4)

**Approved State:**
- ✅ Create, Read, Update (Update marks dependents as Stale, L2-REQ-2.3)
- ✅ Delete (requires Admin role, L2-REQ-2.2)
- ✅ Can be used in all validation operations (L1-REQ-7, L1-REQ-8, L1-REQ-9)

## 6. Example: Complete Workflow/State Model for MVP

### State Diagram

```
┌─────────┐
│  Draft  │
└────┬────┘
     │
     │ [Guard 1: Permission] AND
     │ [Guard 2: Quality Gate] AND
     │ [Guard 3: Completeness]
     │
     ▼
┌──────────┐
│ Approved │
└──────────┘
```

### Transition Table

| Transition | Guard Conditions | Error Codes | Allowed Roles |
|------------|------------------|-------------|---------------|
| Draft → Approved | 1. Permission (Reviewer/Admin)<br>2. Quality Gate (no ambiguous terms, verifiable)<br>3. Completeness (non-empty content) | `PERMISSION_DENIED`<br>`QUALITY_GATE_FAILED`<br>`INCOMPLETE_REQUIREMENT` | Reviewer, Admin |

### Guard Condition Details

**Guard 1: Permission Check**
- **Component:** The Governor → Permission Engine
- **Validation:** `user.role in ["Reviewer", "Admin"]`
- **Error:** `PERMISSION_DENIED` if user.role is "Engineer"
- **Source:** L1-REQ-3 (RBAC), L2-REQ-3.2

**Guard 2: Quality Gate**
- **Component:** The Governor → LLM Orchestrator
- **Validation:** 
  - No ambiguous terms detected (L2-REQ-6.1)
  - Verifiable criteria present (L2-REQ-6.2)
- **Error:** `QUALITY_GATE_FAILED` with list of issues: `["ambiguous terms: ['fast', 'robust']", "unverifiable criteria"]`
- **Source:** L2-REQ-6.4

**Guard 3: Completeness**
- **Component:** The Governor (internal validation)
- **Validation:** `len(requirement.content.strip()) > 0`
- **Error:** `INCOMPLETE_REQUIREMENT`
- **Source:** L2-REQ-2.2 (CRUD Operations)

## 7. If You Skip the Workflow/State Model

### Consequences

#### 1. Ambiguous L3 Requirements

**Without Workflow/State Model:**
- L3 requirements say "System shall block invalid transitions" but don't specify sequence
- Different developers implement different guard condition orders
- Inconsistent behavior across the system

**Example Problem:**
```python
# Developer A implements:
if check_permission() and check_quality():
    transition()

# Developer B implements:
if check_quality() and check_permission():
    transition()

# Result: Different behavior, inconsistent error messages
```

#### 2. Missing Error Handling

**Without Workflow/State Model:**
- No defined error codes
- Developers invent error codes inconsistently
- Error messages are vague or inconsistent
- Users don't know how to fix errors

**Example Problem:**
- Some components return `ERROR_APPROVAL_DENIED`
- Other components return `UNAUTHORIZED`
- Another returns `BLOCKED`
- All mean the same thing, but users see different messages

#### 3. Incomplete Integration Tests

**Without Workflow/State Model:**
- Tests miss edge cases (what if permission passes but quality fails?)
- Tests don't validate guard condition sequence
- Tests don't validate error codes match specification
- Integration bugs discovered in production

#### 4. Difficult Debugging

**Without Workflow/State Model:**
- No clear documentation of expected behavior
- Developers guess at guard condition sequence
- Error logs don't match expected error codes
- Root cause analysis is difficult

#### 5. Poor User Experience

**Without Workflow/State Model:**
- Users see inconsistent error messages
- Users don't know what to fix (error messages don't guide action)
- Users experience different behavior in different parts of the system

## 9. Validation Checklist

For each state transition, ensure the Workflow/State Model defines:

- [ ] **States:** All valid states listed with descriptions
- [ ] **Transitions:** All allowed transitions (from → to)
- [ ] **Guard Conditions:** All guard conditions that must pass
- [ ] **Guard Sequence:** Order in which guard conditions are evaluated
- [ ] **Error Codes:** Specific error code for each guard failure
- [ ] **Error Messages:** User-friendly error messages that guide action
- [ ] **Entry/Exit Actions:** What happens when entering/exiting states
- [ ] **Sequence Diagram:** Visual representation of the transition flow
- [ ] **Integration Tests:** Test cases for happy path and all blocked paths

---

## 10. Summary

A Workflow/State Model is the **missing link** between L2 state behavior requirements and L3 component implementation requirements.

**Without Workflow/State Model:**
- ❌ L3 requirements are ambiguous
- ❌ Guard condition sequence is unclear
- ❌ Error handling is inconsistent
- ❌ Integration tests miss edge cases
- ❌ Debugging is difficult

**With Workflow/State Model:**
- ✅ L3 requirements specify exact guard condition sequence
- ✅ Error codes and messages are consistent
- ✅ Integration tests validate all paths (happy + blocked)
- ✅ Clear documentation of expected behavior
- ✅ Better user experience with actionable error messages

**The L2 requirements (L2-REQ-2.1, 2.4, 6.4) define WHAT the state machine does.**  
**The Workflow/State Model defines HOW state transitions work (guard conditions, sequence, errors).**  
**The L3 requirements define the component-level implementation of that logic.**

All three are needed for complete state transition validation.
